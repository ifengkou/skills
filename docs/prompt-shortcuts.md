# 思维方法提示词速查表

用成熟方法论说明希望模型怎样分析，再补充当前任务的目标、约束和证据。按问题选择方法；下面五种方法可以单独使用，也可以组合使用。

| 遇到的问题 | 方法 | 希望得到的结果 |
|---|---|---|
| 怀疑问题被既定方案限制 | 第一性原理 | 重新确认目标、成因和最小必要方案 |
| 方案看起来成立，需要寻找漏洞 | 对抗性审查 | 能推翻关键假设的反例与失败条件 |
| 多项改动同时生效，贡献不明确 | 消融实验 | 各机制的收益、成本及相互作用 |
| 多个方案都能满足需求 | 奥卡姆剃刀 | 假设更少、复杂度更低的充分方案 |
| 职责混杂，改动相互牵连 | 高内聚、低耦合 | 清晰职责、稳定接口和依赖方向 |

## 第一性原理：重新确认问题

适合怀疑“题目本身可能就问错了”的时候。回到目标、约束和可验证的事实，检查当前方案的前提。

**提示词案例：**

> 不要基于“加 Redis 缓存”这个既定方案继续设计。从第一性原理分析这个接口为什么慢，以及最小必要的解决方案。

这个案例应先辨别瓶颈来自 SQL、网络、序列化、锁竞争还是重复计算，再判断是否需要缓存。如果索引已经能满足性能目标，应说明依据和适用条件。

**补充约束：**

> 列出已验证的事实和待验证的假设。缺少测量数据时，提出最小验证步骤，并说明什么结果会改变建议。

## 对抗性审查：寻找能推翻方案的证据

适合技术方案评审和 Code Review。重点检查关键假设及其失败后果，按证据和影响判断问题。

**提示词案例：**

> 对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。

比如，方案准备通过分布式锁解决重复请求，可以检查：重复请求是否需要互斥，幂等能否满足要求，锁服务不可用或锁先于业务执行过期时会发生什么。

**补充约束：**

> 对每个关键问题，给出触发条件、证据或验证方法，以及对方案的影响。区分已证实的问题与假设风险。

## 消融实验：验证每个机制的贡献

适合多项优化同时加入、总效果变好，却无法判断各项收益的情况。

**提示词案例：**

> 加索引、Redis 缓存和批量查询后，接口耗时从 800ms 降到了 100ms。给这三个优化设计消融实验，判断真正的收益来自哪里。

可以比较基线、单项优化、完整方案移除某一项，以及必要的组合。只比较逐步叠加的几组结果，可能无法区分机制贡献和交互效应。

**补充约束：**

> 固定数据、负载和运行环境，明确缓存冷热状态、测量指标与重复测量方式。设计能区分各机制贡献及交互效应的对照，并报告性能收益和维护成本。

假设实验发现仅加索引就降到 120ms，就可以进一步判断其他机制带来的 20ms 是否值得其复杂度。这里的数字是示例，实际贡献需要测量；缺少数据时，交付实验设计和判断标准。

## 奥卡姆剃刀：选择最小充分方案

适合方案已经包含多个服务、配置或补偿机制，需要检查是否过度设计的情况。比较复杂度时，仍需满足功能、可靠性和运维要求。

**提示词案例：**

> 用奥卡姆剃刀重新审查这个设计，在满足需求的前提下，删除所有非必要机制。

比如，原方案包含 Kafka、Redis、分布式锁、状态机和定时补偿。如果当前约束下一个数据库事务加唯一索引已足够，应说明哪些需求得到满足，以及被删除机制原本承担什么作用。

**补充约束：**

> 对每个保留机制，说明它满足的具体需求或应对的已知失败模式。比较方案的假设、运行成本和维护成本；删除机制后，说明对应责任如何得到满足。

## 高内聚、低耦合：检查职责与边界

适合模块承担多种职责、依赖相互牵连，或者改一个功能总会影响其他功能的情况。

**提示词案例：**

> 按高内聚、低耦合原则审查 OrderService 的职责边界，不要为了拆而拆。

比如，一个 2000 行的 OrderService 同时处理库存、优惠券、短信、支付和报表，应检查哪些行为属于订单职责，哪些变化原因不同，哪些需要通过稳定接口协作。文件行数可以提示调查，但不能直接决定拆分。

**补充约束：**

> 根据职责、变化原因、信息隐藏和依赖方向提出边界。说明拆分减少了什么耦合，以及新增接口和调用关系的成本。

## 组合使用

原始组合提示词：

> 从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。

实际任务中可以按需选择，避免无关的方法增加分析成本。比如，针对一个已经提出方案的架构问题：

> 从第一性原理重新确认目标和约束，对推荐方案的关键假设做对抗性审查，再用奥卡姆剃刀选择最小充分方案。所有结论注明证据；尚未验证的关键点，给出验证方法和通过标准。

涉及多项优化的贡献时，增加消融实验；涉及模块职责调整时，增加高内聚、低耦合分析。方法名称之外，补充当前任务的验收目标、资源限制和允许执行的范围。
